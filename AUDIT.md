## Evidence and reasoning

- History is called after compact scanning and imports reject heights above `block_fully_scanned`; this makes existing scanned-chain rewind detection cover earlier chunks from an interrupted stream.
- Range ingestion bounds decoded batches to 100 transactions and queries to 100 block heights. The cursor remains unchanged until EOF, successful final node-hash validation, and a transactional cursor compare-and-swap against the scanned block hash. Retrying durable earlier chunks uses SDK idempotent writes.
- The additive migration preserves earlier migration identities. Missing cursors backfill from the fixed development-wallet birthday. Coverage is per account/receiver, and the outer loop enumerates receivers again after ingestion can extend lookahead.
- Source account selection reuses `public_transparent_queries`, explicitly restricted to accounts 1–5. Account 6 is excluded from history requests. A transaction involving a public receiver can still contain other wallet outputs; this is normal SDK ingestion, not a query of treasury history.
- Rewind updates SDK state, treasury cursor, and history coverage in one SQLite transaction. The test injects a history-update trigger failure to demonstrate rollback, then tests orphaned and replacement spend accounting with the real SDK.
- Pending spend links do not suppress history queries. The pinned SDK retains a spend map for inputs whose receipts arrive later; cross-address import order therefore does not inherently lose those links.
- `synchronize_wallet_until` publishes only after history succeeds; final snapshot publication checks the scanned checkpoint against the node. The sync lock serializes normal sync and rewind. Cancelled blocking SDK work holds the DB mutex until it completes; a later DB operation cannot race through that lock.
- The pinned [lightwalletd service](https://raw.githubusercontent.com/zcash/lightwalletd/d79cd1100575ff909d70e00d5514a4092df94934/frontend/service.go) implements `GetTaddressTransactions` using node `getaddresstxids` with explicit bounds and raw transaction retrieval. It includes both address inputs and outputs and propagates retrieval failures. It does not use a separate lagging transparent-history cache. Completeness still trusts the configured local service and node address index.
